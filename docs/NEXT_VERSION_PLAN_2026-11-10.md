# 下一版計畫：讓使用者送得出自己的一批工作

日期：2026-11-10
前置文件：`NEXT_RELEASE_AUDIT_2026-11-02.md`、`HCODE_DISTRIBUTED_ROADMAP.md`、`MANAGED_RUNTIME_V2_PLAN.md`

## 目標

一個沒讀過文件的人，拿自己的資料，能在送出前知道這批工作要花多少 CPT，失敗的輸入在花錢前就被找出來，中斷後能接著跑，並且拿到結果檔。

副本共識、結算與授權不在本版範圍。這些已經完成，本版處理的是使用者到達它們之前的那一段。

## 依據

| 觀察 | 位置 |
|---|---|
| 報價只算保留資源，不算執行；CLI 批次的預設單筆上限是 100 CPT，三副本下每副本只剩約 30 單位，稍大的函式都會因預算耗盡而失敗 | `cli.rs` 的 `DEFAULT_BATCH_TASK_CPT` 與其註解 |
| 計費是確定性的：每個副本的用量由來源與輸入唯一決定，任務上限必須包住「副本數 × 用量 + 10% 手續費」 | `task_repository.rs` 的 `managed_v1_total_budget_hold` |
| Master UI 的提交頁只有原始碼框、JSON 框與六個資源欄；沒有模板、語法檢查、費用預覽 | `frontend/master-ui/src/App.jsx` |
| 批次的迴圈在用戶端，CSV 只在最後寫出，中斷後無法接續 | `cli.rs` 的 `run_batch` |
| 歡迎金 1,000 CPT；10×10 `matmul` 每副本 1,110 單位，三副本含費 3,663 CPT | `account.rs`、`HCODE_RUNTIME.md` |

## 設計限制

- Nodepool 是唯一的結算權威。本機試跑只是使用者端的預估，Nodepool 仍以 Worker 回報、副本一致與自己的計算為準；文件與介面都要寫成「預估」。
- 試跑結果不得被描述成「已驗證」。它只代表在這台機器上、以這個版本的直譯器跑出的結果。
- 官網不新增任何提交或操作功能。提交留在 Master UI、CLI 與 Master HTTP API。
- `check` 與批次預檢在本機離線執行，不需要帳號。Master 的試跑端點本身不呼叫 Nodepool，也不需要帳號餘額，不產生任何扣款；但它與其他 Master 路由一樣經過登入與 VPN 閘門，閘門在需要外部覆蓋網路時可能要求連線。
- 不降低 quorum，不忽略擁有者規則，不信任 Worker 自報的計費。

## 切片

每個切片獨立提交，測試通過後才提交，只提交到本機。

### S1　共用計費算術與本機試跑

問題：沒有任何一處能回答「這個函式、這筆輸入要多少 CPT」。

做法：

1. `general-compute-runtime` 新增 `managed_budget` 模組，收納手續費、最壞情況保留額、任務總預算反推每副本額度，以及新增的 `required_task_budget(每副本用量, 副本數)`。`task_repository.rs` 的同名函式改為呼叫它，避免兩份計費算術。
2. `managed-function-runtime` 新增 `dry_run`：以與 Worker 相同的限制（預算、輸出上限、取消旗標）跑一次，回傳結果、輸出、用量、迴圈與呼叫計數，或帶行列號的結構化錯誤。支援 `TensorArtifacts`。
3. 試跑有自己的牆鐘時限與用量上限，避免卡住 Master 或 CLI。

驗收：

- 用量 25 的 `sum-list` 範例，三副本的任務上限為 82 CPT；以 82 反推每副本額度得 25。
- 以剛好等於用量的預算執行成功，少 1 單位時失敗並回報預算耗盡。
- `task_repository.rs` 既有的預算測試（`managed_v1_total_budget_uses_equal_replica_allowances_and_fee` 等）全部不改動即通過。

### S2　Master HTTP 試跑端點與 `hivemind check`

做法：

- `POST /api/tasks/dry-run`：需要 Master 登入；收 `task_source`、`torrent`（輸入）與選填的副本數；回傳預估的每副本用量、任務上限、手續費、輸出預覽與結構化錯誤。以信號量限制同時執行數，在 `spawn_blocking` 內執行。
- `hivemind check <source> --input <json> [--artifact name=path] [--replicas <n>] [--max-usage <units>] [--timeout-secs <n>]`：離線執行，不需要帳號。只收行內 JSON，與 `submit` 一致。
- `hivemind submit --max-cpt auto`：先試跑，以預估的任務上限送出。

驗收：端點與 CLI 對同一份來源與輸入給出相同的用量與上限；超過來源或輸入大小上限時回 400；未登入回 401；語法錯誤回傳行列號。

### S3　批次預檢與逐筆上限

做法：`hivemind batch` 在送出前對每一筆輸入本機試跑。

- 失敗的輸入列出行號與原因；預設整批不送出，`--skip-invalid` 時只送出通過的，失敗列在結果 CSV 標為 `PRECHECK_FAILED`。
- 未指定 `--max-cpt-per-task` 時，每筆用自己的精確上限；總額為各筆上限相加，與 `--max-total-cpt` 比較。指定時視為固定上限，用量超過它的輸入同樣在預檢被擋下。
- 預檢預設開啟，`--no-precheck` 關閉。副本數預設以網路預設的 3 估算；指定 `--replicas` 時，副本數與對應的 quorum 會隨任務送給 Nodepool，讓報價與實際策略一致。

驗收：函式對某一行拋錯時，該行在任何任務送出前就被指出；總額為各筆上限之和；預設行為不再產生因 100 CPT 上限而失敗的批次。

### S4　批次續跑

做法：首次執行寫出狀態檔（來源與每筆輸入的 SHA-256、每筆上限、副本數、任務前綴）。`--resume` 先核對狀態檔，再向 Nodepool 查出已存在的任務，只送出缺少的；其餘直接取得目前狀態。任務 ID 由前綴與序號決定，所以不需要另外的進度記錄。

驗收：中斷後以 `--resume` 重跑，不會重複送出或重複扣款；來源或輸入有任何改動時拒絕續跑並指出原因；沒有狀態檔時拒絕。

### S5　Master UI 提交流程

做法：

- 模板選單：八個模板，內容逐字等於 repo 已在測試中執行的程式（`templates/hcode` 與官網文件範例），由 Node 測試比對，所以不會與被驗證的程式脫節。
- 「試跑與費用」面板：呼叫 S2 的端點，顯示輸出預覽、每副本用量、預估上限與手續費、錯誤的行列號；一鍵把預估上限填入上限欄。
- 六個資源欄收進「進階」；欄位說明與提示文字改為「hcode 原始碼」，移除暗示可用自然語言描述的措辭。
- 任務列表直接展開輸出，提供複製與另存；失敗時顯示失敗原因與是否扣款。

驗收：純邏輯放在 `.mjs` 模組並有 `node --test` 測試；Vite 建置通過；英文與繁體中文訊息同步。

與原計畫的差異：

- `check` 不接受 `--input-file`。`submit` 刻意只收行內 JSON，兩者保持一致。
- 失敗輸入的判斷與價格無關，所以預檢後、登入前就先檢查；被拒絕的批次不會發出任何請求。
- 只有語法錯誤帶行列號。直譯器目前只在剖析階段記錄位置，執行階段的錯誤沒有，介面不顯示不存在的位置。
- 建議的上限不只是工作本身的費用：Master 會拒絕低於資源報價的 `max_cpt`，而資源報價每台至少 10 CPT。`submit --max-cpt auto` 與批次預檢取工作上限與資源報價兩者較大值；`check` 只估算工作本身，輸出已標明此點；UI 試跑後另外向 `/api/tasks/quote` 查資源價格。
- 試跑面板固定以網路預設的 3 個副本估算；`check` 與批次預檢可用 `--replicas` 改變副本數。網路若設定了不同的預設值，估算會偏離。

## 本版不做，以及原因

| 項目 | 擱置原因 | 需要的決定 |
|---|---|---|
| 伺服器端 Job、HTTP 批次 API、API token、Python SDK | 需要 Nodepool 資料表、proto 與長效憑證，屬信任邊界變更；沒有 token 時 SDK 只能保存密碼 | 先寫設計文件，確認憑證模型與撤銷方式 |
| 向量化內建函式改用批量計價、定期免費額度 | 前者會更換 `hcode-execution-cpt-v1` 的成本模型識別，受 V2 計畫的 Gate 1 與 Gate 2 約束；後者動用有限的系統池 | 產品與額度政策 |
| 預設改為先派兩個副本 | 實測每筆 CPT 少 31%，但逾時情境較慢；V2 計畫將其列為 D | 是否接受收費預設變更 |
| 由 Nodepool 抽樣重算已認證結果 | 屬於驗證層級的新增，且驗證節點不能放在 Orange Pi；需與「聲譽不取代答案驗證」的規則一併決定 | 信任模型與驗證節點的位置 |
| hcode 語言補齊（註解、`while`、清單附加與排序、字串函式） | 每次語言變更都會改變語意清單的摘要，必須先確認舊 Worker 的處理方式與更新通道 | 發布流程就緒後再排 |
| 程式碼簽章與啟用更新通道 | 需要簽章憑證與更新清單的託管位置 | 使用者提供憑證與位置 |
| Linux headless Worker、Worker UI 分享設定 | 供給面工作，與本版的需求面目標分開 | 排入下一版 |
| P2P 傳輸接線 | 既有函式庫保持原狀；單一張量上限 100,000 個元素，傳得進去也算不動 | 排在額度補洞之後 |

## 風險

- **本機與 Worker 的直譯器版本不同。** 用量可能不同，Worker 端因預算不足而失敗，這種情況不收費。預估上限只在版本一致時精確；介面與文件都標註預估，`check` 的輸出附上語意清單摘要，方便對照。
- **試跑吃掉 Master 資源。** 以用量上限、牆鐘時限與同時執行數限制；超過上限時回報「超過試跑上限」，使用者仍可手動指定上限送出。
- **批次預檢拖慢啟動。** 預檢是本機計算，只在函式本身很重時才明顯；`--no-precheck` 可關閉。

## 驗證

- `executor-rs`：`cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets --all-features -- -D warnings`、`cargo test --workspace`。
- `hivemind-rs`：同上三條。資料庫相關測試在沒有 Postgres 時會被略過，綠燈不代表通過，必須連上真實資料庫執行。
- `frontend/master-ui`：`npm test`、`npm run build`。
- 每個切片以 `check` 或試跑端點對 `docs_examples.rs` 的既有範例做交叉驗證：用量必須與已發布的數字一致。
