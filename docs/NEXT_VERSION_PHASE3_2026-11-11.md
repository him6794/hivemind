# 第三階段：模型分段、管線與閒置貢獻（2026-11-11）

前置文件：`NEXT_VERSION_PHASE2_2026-11-11.md`、`HCODE_DISTRIBUTED_ROADMAP.md`、`HCODE_RUNTIME.md`。

## 目標

1. 用戶端能把超過單一任務上限的模型切成多段，交給不同的 Worker 執行，每一段照舊由副本共識驗證。
2. 同一套機制能執行「多台裝置各算一份資料，再合併」的小型訓練回合。
3. Worker 能設定為只在電腦閒置時接工作。

三項都落在用戶端：前兩項在 CLI，第三項在 Worker。Nodepool 的派工、共識與結算不變。

## 範圍

本階段的「拆分」是下面兩種，兩者都以一般的 hcode 任務執行：

- 依層切段：連續的幾層放在同一個任務，前一段的輸出是下一段的輸入。
- 依列切片：一層的權重放不進單一任務時，把輸出列分給同一階段的多個任務，同時在不同的 Worker 上執行，下一段再合併。

不在本階段內：

- 逐 token 的互動式語言模型推論。每一段都是一次完整的任務（派工、多副本執行、共識），延遲以秒計。
- GPU 執行。`hcode-gpu` 是另一條結算路徑，沒有 CPU 副本共識，逐位元一致的假設不適用。
- 經 P2P 分發權重。權重仍由 CLI 逐任務上傳到 Nodepool。
- 對 Worker 保密。被指派的 Worker 會收到該段的權重與中間結果。

## 依據

以下數字都來自目前的程式碼或本機實測。

| 限制 | 數值 | 位置 |
|---|---|---|
| 單一值（含張量）的標準 JSON 大小 | 1 MiB | `managed-function-runtime/src/lib.rs` 的 `max_value_bytes` |
| 單一張量的位置數 | 100,000 | 同上，`max_collection_items` |
| 一次執行累計配置的值大小 | 16 MiB | 同上，`max_value_materialization_bytes` |
| 任務的 JSON 輸入 | 1 MiB | `proto/src/lib.rs` 的 `MANAGED_JSON_INPUT_MAX_BYTES` |
| 共識結果（任務輸出） | 256 KiB | 同上，`MANAGED_CONSENSUS_RESULT_MAX_BYTES` |
| 張量檔 | 每檔 64 MiB、每任務 16 個、合計 256 MiB | `managed-function-runtime/src/artifacts.rs` |

張量的大小以標準 JSON 文字計算，不是以 8 位元組計算。由 F32 權重轉成的浮點數通常印成 19 到 24 個字元，所以單一張量實際上約 4 到 5 萬個元素。實測：40,000 個元素（每個 19 字元）可以建立，60,000 個（每個 17 字元）失敗。

累計上限也計入讀取。每讀一次變數就計入該值的大小：一個約 800 KB 的張量讀 12 次可以完成，讀 25 次就超過上限。因此單一任務能處理的權重大約是幾十萬個參數，超過就必須分段，這是本階段要解決的問題。

任務輸出上限 256 KiB 決定了段與段之間能傳多少：以每個元素約 22 個位元組計，一個任務的輸出大約是 11,000 個元素（特徵數乘以批次大小）。

計價沒有改變：一個乘加是一個用量單位，一個用量單位是 1 CPT。向量化計價仍受 `MANAGED_RUNTIME_V2_PLAN.md` 的兩個閘門約束。在這個價格下，模型推論在公開網路上很貴；本階段完成的是機制，不是價格。

## 設計決定

### 管線由用戶端編排

管線的每個項目是一個獨立的任務，由 Nodepool 各自收件、派工、驗證與計費。CLI 負責把前一階段的輸出組成下一階段的輸入，並依序送出。

理由：

- 分段需要每個任務帶自己的權重檔，而權重檔目前綁定在任務上，由用戶端在任務建立後上傳。伺服器端的 Job 在執行途中才建立後續任務，沒有地方取得這些位元組。要在 Nodepool 端編排，得先做出可跨任務重用的 artifact 儲存，這是另一件工作。
- Master 與 CLI 本來就是不可信的參與者。管線是擁有者對自己任務的安排，不需要 Nodepool 背書；每一段的結果仍由副本共識決定。
- 不改 proto、資料表與結算路徑。

代價：CLI 必須保持執行。中斷後以狀態檔接續，做法與 `batch --resume` 相同。

### 管線的資料流

每個項目的任務輸入是：

```json
{"params": <該項目的固定參數>, "previous": [<前一階段各項目的輸出，依序>]}
```

第一階段的 `previous` 是只有一個元素的清單，內容是整條管線的輸入。每個項目的輸出必須是 JSON 值；函式以 `return` 回傳值，不使用 `print`。

### 新增 hcode `concat`

`concat(list)` 沿第一個維度串接張量。同一任務內的列區塊，以及下一段要合併的多份輸出，都需要它。現有的 `append` 每次都重建整個清單，逐列串接的用量與配置量都是平方成長。

這是語言變更，依就地更新方針處理：更新語意清單與八處摘要，Worker 與 Nodepool 必須同版。

### 每段的上限在切段時量出

切段時在本機以樣本輸入跑完整條管線，量出每個項目的用量，換算成上限寫進管線檔。產生的程式沒有依資料分支的地方，所以形狀相同的輸入用量相同。之後以相同形狀的輸入執行時，不必先在本機重算一次。

本機試跑使用比 Worker 更緊的大小上限，留下餘裕；中間結果的文字長度會隨數值變化。

### 閒置判斷只在 Worker 本機

Worker 自己判斷電腦是否閒置，不閒置時在心跳中回報 `BUSY`，並在本機拒收新的執行與權重準備。已經在執行的任務會跑完，不中斷。

2026-11-12 審查修正原先假設：現有共識排程器刻意將 `BUSY` 納入隨機選樣，避免依 Worker 自報的狀態選擇副本；不能只靠心跳阻止執行。本階段不更動這個 Nodepool 規則，也不降低副本數。本機拒收後可能無法達成共識而失敗，其他副本的有效工作仍可能計費，不能承諾透明補派。

這是 Worker 對自己可用性的宣告，不涉及結果或計費的信任。

### 與已公開專利申請的關係

本階段的設計依據是公開多年的做法：志願運算在閒置時執行工作（BOINC），以及各裝置在本地訓練後取平均（FedAvg，2016）。微軟申請案 US 2026/0349820 A1 的請求項我沒有讀到，所以無法判斷是否落入其範圍。這不是法律意見；要商業化時應請專利律師核對請求項。

## 切片

每個切片獨立提交，測試通過後才提交，只提交到本機。

### P1　hcode `concat`

- `concat(list)`：清單至少一個張量；各張量的 dtype、秩與第一維以外的形狀必須相同；結果的第一維是各張量第一維的總和。
- 用量：結果的每個位置一個單位，在串接前收取。結果受位置數與值大小上限約束。
- 名稱列入保留名稱。只在 CPU hcode 生效，frozen v0 不變。

驗收：串接向量與矩陣的結果正確；形狀或 dtype 不符、空清單、非張量元素都失敗並有明確訊息；用量等於結果的位置數加上運算式本身的成本；超過位置上限時在配置前失敗；語意清單摘要與八處固定值同步更新。

### P2　`hivemind pipeline check`：本機跑完整條管線

- 管線檔（JSON）：`stages` 清單，每個階段有 `items`，每個項目有 `source`（路徑）、選填的 `params` 或 `params_file`、選填的 `artifacts`（名稱對路徑）、選填的 `max_cpt`。路徑相對於管線檔。
- `check` 依序在本機執行每個項目，以前一階段的輸出組成輸入，印出每個項目的用量、所需上限、輸出大小，以及最後一個階段的輸出。
- 檢查三個大小：組成的輸入不超過 1 MiB，每個輸出不超過 256 KiB，輸出是合法 JSON。任何一項不符都指出是哪個階段的哪個項目。

驗收：兩階段、含平行項目的管線在本機得到預期輸出；某個項目失敗時指出位置與原因，不繼續執行；輸出超過 256 KiB 時在本機就被擋下。

### P3　`hivemind pipeline run`：送到網路執行

- 逐階段送出：同一階段的項目一起送出，全部完成後才組下一階段的輸入。有權重檔的項目在任務建立後上傳。
- 上限：管線檔有 `max_cpt` 就用它；沒有就在送出前於本機試跑該項目取得。上限不低於 Master 的資源報價。
- 總額：`--max-total-cpt` 必填。送出一個階段前，已計費金額加上該階段各項目的上限不得超過它。
- 狀態檔：記錄管線與輸入的摘要、任務前綴、每個項目的任務 ID、狀態、計費與輸出。`--resume` 核對摘要後接續；已完成的階段不重跑，失敗的項目以新的任務 ID 重送。
- 任一項目失敗就停止，指出項目與 Nodepool 回報的原因。
- 結果寫到 `--out`，並印出最後一個階段的輸出。

驗收：以本機假 Master 測試送出順序、輸入組成、上限、總額拒絕、失敗停止、續跑不重送已完成的項目、摘要不符時拒絕續跑。

### P4　`hivemind model`：把模型切成管線

- 模型描述（JSON）：依序的層。`linear`（權重 `[out, in]`，選填偏置 `[out]`）、`relu`、`gelu`、`softmax`。權重來自 safetensors 檔，支援 F32 與 F64。
- `model init <weights.safetensors>`：從檔頭讀出 `N.weight`／`N.bias` 這種依序命名的張量，產生模型描述。活化函式不在權重檔內，以 `--activation` 與 `--final` 指定。
- `model split <model.json> --weights <file> --input <json> --out-dir <dir>`：
  - 依權重的實際文字大小，把每層切成不超過單一張量上限的列區塊。
  - 依每個任務的配置預算，把區塊裝進項目：放得下的連續幾層放在同一個項目；單層放不下時，把該層的列分給同一階段的多個項目。
  - 為每個項目寫出 hcode 原始碼與只含該項目權重的 safetensors 檔。
  - 在本機以樣本輸入跑完整條管線，量出每個項目的用量與上限，寫進 `pipeline.json`。超過大小上限時縮小預算重切，仍不行就回報是哪一層、為什麼。
- 輸入是一批樣本 `[[...], ...]`，輸出是每個樣本一列。

驗收：同一個模型以很小的預算切成多段多片，與放在單一項目的結果逐位元相同；與測試中獨立計算的參考值在容差內一致；切出的每個項目都在 Worker 的大小上限內；放不下的情況有明確訊息。

### P5　小型訓練範例

- 以 P2／P3 的管線表達聯邦平均：每一回合有一個平行階段（每個項目用自己的資料分片，從目前的權重做幾步梯度下降）與一個合併階段（取平均）。
- 模型是 softmax 迴歸。資料與管線檔由標準函式庫的 Python 指令稿產生，資料是合成的。
- 範例放在 `examples/hcode/federated-training/`。

驗收：測試在本機跑完整條管線，損失逐回合下降，結果與固定的期望值一致。

### P6　Worker 只在閒置時接工作

- 設定：分享模式 `always`（預設，與現在相同）或 `idle`；閒置門檻（多久沒有鍵盤滑鼠輸入算閒置）。
- 判斷：Windows 以最後一次輸入的時間判斷。沒有互動工作階段的環境（Linux headless）沒有輸入可量，`idle` 模式改以系統 CPU 使用率判斷，並在介面與文件寫明。
- 回報：`idle` 模式下不閒置時回報 `BUSY`，閒置時回報 `IDLE`。
- 本機控制 API 與 Worker UI：顯示目前模式與是否正在接工作，可以切換。

驗收：純邏輯（模式、門檻、狀態轉換）有單元測試；心跳在兩種狀態下送出對應的狀態；控制 API 需要登入；UI 測試與建置通過；英文與繁體中文訊息同步。

- 手冊、教學與範例說明。
- 以本機的 Nodepool、Master 與三個 Worker 實際執行一條切出的管線，記錄每段的用量、計費與時間。同一台機器上的三個 Worker 不代表跨主機，結果如實標註。

### 採用的細節

- P3 的 `--task-prefix` 可省略並自動產生；`--resume` 必須給同一前綴。任務 ID 從 `prefix-1-1` 起，重試用 `-r1`、`-r2`。每次建立前保存狀態，回應不確定時先查原 ID，不另建可能重複計費的任務。
- 摘要涵蓋輸入、原始碼、參數與權重內容，且送出前核對實際保留的位元組。上限不納入摘要，所以預算不足後可調高再續跑；歷次費用與未結算上限仍全部計入。`billing_settled=false` 時不能把 API 的零金額當成免費。
- JSON 結果檔包含成功、部分結果與失敗原因。完全沒嘗試送出的新執行不留狀態檔；有過送出嘗試，即使被拒、回應遺失或逾時，也保留可接續的紀錄。
- 管線預設明確要求三副本，請求、估價與狀態檔使用同一數字。`model split`、`pipeline check` 與 `pipeline run` 均支援 `--replicas 2..7`。舊草稿的狀態若未固定實際副本政策，不能安全猜測，續跑會拒絕。
- P4 以實際 canonical JSON 大小和 Worker 限制量測。中間張量採特徵列，最後轉回樣本列；softmax 在完整特徵合併後執行。中間結果若太大，仍嘗試與下一個縮小形狀的層打包，避免錯誤拒絕可執行模型。
- P5 是三個分片、四回合 softmax 迴歸；固定參考損失由 `1.0986122886681098` 降至 `0.2206224401578563`，獨立參考容差 `1e-12`。這不是用浮點容差取代副本共識。
- P6 的心跳之外另有本機接收檢查；檢查在身分驗證後，且執行器在登錄新任務時再檢查一次。執行中請求可加入等待，已快取回應可重取；完成到快取發布之間的重複請求仍可能暫時收到 `Unavailable`，但不會因此再執行一次。
